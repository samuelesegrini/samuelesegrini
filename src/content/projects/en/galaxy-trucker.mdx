> Final project of the 2024–2025 Software Engineering course at Politecnico di Milano (group GC26, taught by Gianpaolo Cugola). Four of us translated Cranio Creations' board game Galaxy Trucker into a distributed Java application: one authoritative server, multiple clients, two network transports and two interfaces.
>
> In my path this is where software stopped being a sum of classes. A command that is correct locally is not enough when it has to cross the network, mutate shared state exactly once and come back consistently to four different interfaces. This page describes the system we shipped, my contribution, the limits of the archived artifact and the reconstruction I did a year later.

## The problem

Galaxy Trucker is played in two very different phases. During construction, players draw components simultaneously from a shared pool and mount them on their ship, respecting connector adjacency rules and forbidden positions. During flight, a sequence of adventure cards (pirates, planets, meteor swarms, open space, war zones, epidemics) alters ships, crews, credits and board positions according to turn-based choices.

The course specification required the complete level II ruleset, automatic ship validation, real-time visibility of the other ships, an MVC client-server architecture, Socket and RMI connections even within the same game, and two clients: a textual one (TUI) and a graphical one (JavaFX). As advanced features we added the test flight and simultaneous games on the same server.

The engineering knot is consistency. State has four different natures: the shared component pool, each player's public table and private hand, turn-dependent cards, and several games living in a single process. Every action starts on a client and must be validated once, applied once and made visible to everyone.

## Architecture

The code is organised by role into three roots: `server`, `client` and `common`. On the server, the domain (`model/domain`) separates ship and components, crew, flight board, adventure cards and configuration loaded from JSON. Coordination lives in `server/core`: `GameSessionManager` owns the games, `PlayerSessionRegistry` binds identities to sessions, `ConnectionMonitorService` handles heartbeat and disconnections.

Communication follows the Command pattern with self-contained requests: 22 request types plus 9 for flight, 34 response types and 47 events (32 general, 15 flight) defined in `common/message`. A request reaches the server, is validated against authoritative state, and produces a response for the sender and an event for everyone else. The event is the only way a client learns that the world has changed.

The two transports are symmetric adapters: `SocketServerAdapter` and `RMIServerAdapter` on the server, `SocketNetworkAdapter` and `RMINetworkAdapter` on the client. Above them the rest of the system sees a single network interface, so the protocol is a startup parameter rather than a fork in the code. Java serialisation carries the messages; Jackson loads configuration and decks.

Adventure-card logic uses the Visitor pattern: `AdventureCardVisitor` resolves eight card families with different rules (combat strength with directional cannons and batteries, meteor defence with shields, exposed-connector counting, cabin connectivity for epidemics). `FlightBoard` keeps positions with collision prevention and recomputes leadership after every move.

## My contribution

I authored 121 of the 314 commits on the main branch. The history shows where I worked: the initial package and model structure, the RMI transport, the internal command and event system, authentication, the heartbeat service, the session registry for multi-game support, the construction-phase controller with forbidden positions, and the game-data loading logic.

Towards submission the work became cross-cutting: wiring interface navigation to client state, fixing the listener structure and serialisation, resolving the circular dependency between player and ship, fixing double draws, timers and player colours. The final weeks of commits are almost all `fix(...)`: it is the phase in which a distributed system reveals the errors no single class would have shown.

Rules, interfaces, tests and delivery were shared responsibilities with Manuela Terribile, Alessandra Varricchio and Diego Zanca. These are my contributions, not a claim of authorship over the whole.

## What can be verified, and what cannot

The repository holds 272 source files and 63 JUnit 5 test classes with Mockito, the delivered JARs under `deliverables/` and the protocol documentation. The academic scope was completed and graded.

The final snapshot has a defect I declare rather than silently fix: `ClientApp` imports `newGUI` and `newUI` from the `client.ui` package, but only `newTUI` survives in the tree. A clean build of `main` fails before reaching the game. Completion is a historical state of the project; reproducibility is a present technical state, and a portfolio has to say which of the two it can demonstrate.

## One year later: the reconstruction

In August 2026 I returned to the same requirements on the `develop` branch: 146 commits in four days, alone, with Claude as a collaborator. I directed the milestones, evaluated the architectural proposals and verified behaviour against the published rules and requirements.

The central choice is documented in `SIMPLE-DIRECT-MODEL-ARCHITECTURE.md`: the client uses the server models directly instead of a parallel local state. `LocalGameState`, 691 lines with fifteen conversion methods, is replaced by a `ClientState` of roughly 150 lines that receives the updated model and asks the views to `refresh()`. The flow becomes request, server update, response to the requester plus event to the others, redraw.

It was not a blind test of an AI's ability to rediscover decisions: documentation and code were available. Method, convergences and differences are in [Rebuilding Galaxy Trucker with Claude: what changed, what did not, and how to measure it](/en/writing/rebuilding-galaxy-trucker-with-claude/).

## What I carry forward

Distributed behaviour is an integration problem before it is a class-design problem: explicit contracts between components and whole-system verification matter more than local correctness. The reconstruction added a second lesson, which I now apply to iOS development: when requirements, decision criteria and checks are written down, an automated collaborator genuinely accelerates, and responsibility for the result stays mine.
