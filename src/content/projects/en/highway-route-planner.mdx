> An individual project developed for the 2022–2023 Algorithms and Data Structures final assignment. The program maintains a mutable highway, manages electric-vehicle fleets, and computes valid journeys in either direction.
>
> The main difficulty was not only finding the fewest stops: the solution also had to enforce a precise preference rule between tied routes while remaining correct after stations and vehicles were inserted or removed.

## From specification to problem

The specification models a highway as a sequence of service stations. Each station is uniquely identified by its distance from the beginning of the highway and provides a fleet of electric vehicles. Every vehicle has its own driving range and can only reach stations within that distance.

The system must support data that changes over time: a station can be built or demolished, while vehicles can be added or scrapped. The program then plans journeys between existing stations using the current state of the highway.

The constraints make route planning more involved than checking a single distance:

- a journey cannot reverse direction;
- a new vehicle is rented at every stop;
- each station can hold up to 512 vehicles with different ranges;
- the route must use the fewest possible stops;
- tied routes must follow the preference order defined by the specification.

The result is not only a path-finding algorithm. It is a small mutable system that must keep stations, fleets, and subsequent requests consistent.

## Data model

I modelled a vehicle through its driving range and a station through three pieces of information: distance, vehicle count, and a pointer to the fleet array. The highway itself is a dynamic array of stations kept in ascending distance order.

This ordering is the structure’s main invariant. It allows `findStationIndexByDistance` to use binary search instead of scanning every station. The same order also makes it natural to traverse the highway from left to right or from right to left during route planning.

## Command handling

Five commands insert or remove stations and vehicles, then plan a route or report that none exists. Binary search handles station lookup; `malloc`, `realloc`, `free`, and `memmove` maintain the ordered dynamic structures.

## The route as an implicit graph

The core of the project is `findOptimalPath`. I treated each station as a node and every possible move as a directed connection: an edge exists from the current station to a later station when at least one available vehicle has sufficient range.

The graph is never built or stored explicitly. Connections are evaluated when needed by comparing the distance between two stations with the ranges in the departure fleet. The direction of travel determines the scan order: `+1` when the destination is farther along the highway and `-1` when travelling towards its beginning.

Two arrays retain the minimum moves and selected predecessor. Reachable stations update later candidates in travel order; the destination is then traced back through its predecessor chain and printed from origin to destination.

## Tied routes

The specification does not accept an arbitrary answer when several routes use the same minimum number of stops. Working backwards from a shared final sequence, it requires the route containing the station with the shorter distance from the beginning of the highway.

The code handles ties while updating a predecessor: when the step count is equal, it retains the candidate with the lower distance. This detail matters particularly for reverse journeys, because preference depends on absolute distance from the beginning of the highway rather than the direction of travel.

In the specification’s example, `20 → 30 → 50` must be selected over `20 → 45 → 50`. For the opposite journey, the required sequence is `50 → 30 → 20`.

## Complexity and trade-offs

Route planning compares pairs of stations and may scan the departure fleet to test each possible move. Its worst-case cost is therefore `O(n² · v)`, where `v` is the number of vehicles per station and the specification caps it at 512. The minimum-step, predecessor, and reconstructed-route arrays require memory linear in the number of stations.

This solution favours a direct and readable representation. It is not the most sophisticated structure possible, but it keeps ordering, reachability, and route reconstruction explicit.

## What I learned and what I would improve

The project required me to reason about invariants, memory, and algorithms together. A data structure is useful not only because it stores the right information, but because it makes the operations performed on that information reliable and understandable.

Today I would separate parsing from domain logic, handle allocation failures consistently, isolate tie-breaking, and test reverse and unreachable routes. Caching each station’s maximum range would also avoid scanning a whole fleet merely to establish reachability.
